4. Designing Your Firestore Database Structure
This is the step most beginners rush — and regret later. Good structure now = fewer headaches
later.
Core Concepts
• Collection → like a folder/table (e.g., users, listings, ratings)
• Document → like a single row/record inside a collection (e.g., one user)
• Field → like a column/property inside a document (e.g., name, email, avgRating)
• Sub-collection → a collection nested inside a specific document

└── \{userId\} (document)
├── name: string

├── following_count: int
└── created_at: timestamp
listings (collection)
└── \{listingId\} (document)
├── title: string
├── description: string
├── owner_id: string (reference to users)
├── location: geopoint
├── avg_rating: double
├── total_ratings: int
├── photos: list
└── created_at: timestamp
ratings (collection)
└── \{ratingId\} (document)
├── listing_id: string
├── user_id: string
├── rating_value: double
├── comment: string
└── created_at: timestamp
Design Principles to Follow
10. Keep documents flat where possible — avoid deeply nested objects; Firestore queries
work best on top-level fields.
11. Use references (document IDs) instead of duplicating large data — e.g., store owner_id,
not the entire user object, inside a listing.
12. Denormalize for performance when needed — e.g., storing avg_rating and total_ratings
directly on the listings document (synced via a Cloud Function) avoids expensive
aggregation queries every time.
13. Plan your collections around your screens — ask: "What data does each screen need to
query?" That usually reveals your collection structure naturally.
14. Use consistent naming — pick either camelCase or snake_case for field names and
stick with it across the entire project.

6. Firestore Security Rules — The Basics
Security rules control who can read/write what. By default, FlutterFlow sets reasonably safe
rules, but you should understand and review them.
Step 1: Open Rules in Firebase Console
• Go to Firebase Console → Build → Firestore Database → Rules tab.
